# Choosing the interaction

The interactive section is the one that most often collapses into decoration.
The reliable way it fails: a tabbed panel, a collapsible list, or a hover
tooltip gets added, technically satisfies "interactive," and teaches nothing —
because the reader can absorb all of it by scrolling past.

The test that separates the two is whether the reader has to **predict, then
check**. If they can get the information without committing to an expectation
first, you have built a disclosure widget, not a learning instrument. Being
wrong about a prediction is what makes a mechanism stick.

A second test, almost as useful: could this same widget be dropped onto a
different PR unchanged? If yes, it is generic chrome. The interaction should
be so specific to this change that it would be nonsense anywhere else.

## Match the interaction to what kind of change it is

These are starting points, not a menu to pick from mechanically. The point is
that different bugs have different shapes, and the shape suggests its own
instrument.

**A boundary or threshold bug** — off-by-one, a limit, a size where behavior
flips. Give the reader the parameter. A slider or number input that runs both
the old and new logic and shows the two answers side by side, with the flip
point somewhere they will hit by accident. They should be able to *find* the
boundary themselves rather than be told where it is.

**Catastrophic backtracking, complexity, or anything exponential.** Let them
drive the input size and watch a real measured cost — actually run both
implementations in JS and time them, or plot steps against `n`. A table of
"n=14: 0.001s, n=24: 1.1s" that they generated by moving a slider lands
harder than the same table printed as static text, because they watched it
happen.

**A race, a lifecycle bug, or anything order-dependent.** Build a stepper.
Two or more timelines they advance one tick at a time, with the shared state
rendered at each step. Let them choose the interleaving that breaks it. This
is the single best instrument for concurrency, because the whole difficulty of
a race is that you cannot see the interleaving — so show it.

**A parser, regex, matcher, or validator.** A live input box. They type,
they see accept or reject, plus whatever internal detail matters (which branch
matched, how many steps it took). Seed it with the exact adversarial input
from the PR, but let them edit it — the moment they discover a string they
expected to pass and it doesn't is worth three paragraphs.

**A precedence or resolution chain** — config layered over env layered over
defaults, feature flags, a fallback ladder. Toggles for each source in the
chain and a live display of the resolved value. Precedence bugs are almost
always "I didn't realize *that* one wins," which a reader discovers instantly
by flipping switches and never discovers by reading an ordered list.

**A data pipeline or multi-stage flow.** A clickable stage diagram where
selecting a stage shows the shape of the data entering and leaving it. Works
well when the PR changes one stage and the reader needs to see what that does
downstream.

**Refactors, migrations, and moves.** Structure is the subject, so make the
structure interactive: a before/after tree they can toggle, showing what moved
where, with the import graph redrawn. Pair it with the question the reader
actually has, which is "what would break if I still imported the old path?"

**CI, build, and workflow changes.** A simulated run with real measured
timings from the PR, where they can toggle the change on and off and watch
total duration and failure point move. `#1884`-style work — moving a gate
earlier — is invisible as prose and obvious as a bar that shrinks.

**A genuinely mechanical PR** — a dependency bump, a rename, a formatting
pass. Do not manufacture an interaction. Say the change is mechanical, show
what to verify, and keep the artifact short. A forced widget on a trivial
change signals that the whole artifact is padding, which undermines the
sections that do matter.

## Building it

- **Compute honestly.** Where you can actually run both implementations in
  JavaScript, do — a real reimplementation the reader can poke at beats a
  lookup table of precomputed answers, and it stays correct at inputs you
  didn't anticipate. Where the real thing can't run in a browser (a warehouse
  query, a cloud API call), simulate it and *say* you are simulating, with the real
  observed values as anchors.
- **Seed with the real case.** Whatever input actually triggered the bug in
  production or in the test suite should be the default state. Then let them
  wander.
- **Reveal after commitment.** For predict-then-check, keep the answer behind
  an action. A "Run" button, a submitted guess, a stepped tick — anything that
  makes them decide first.
- **Show the reasoning, not just the verdict.** "Rejected" teaches less than
  "rejected — the `'` at index 12 is outside the allowed class." The
  intermediate state is where the mechanism lives.
- **Keep it operable.** Real focus states, keyboard support, sensible ranges
  that can't be dragged into a hang. If a slider can lock the tab by running
  an exponential algorithm at n=200, cap it and label the cap.

## One is enough

A single interaction the reader actually uses beats three they skip. Spend the
effort on making one instrument genuinely revealing about *this* change,
rather than covering several archetypes shallowly.
