# Harness profile: amp

How pstack's own needs map onto Amp. Built and maintained per [`../references/adapting.md`](../references/adapting.md); need IDs come from [`../dialects/cursor.json`](../dialects/cursor.json) and each set's `extra_needs` in `sets/<set>/set.json`. The needs that name discovery fields there take Amp's facts from the repository's `.nthplusio-skills/discovery.json`, so they have no row here. That now includes `modes` (`skills.frontmatter`) and `custom-subagents` (`helpers.definitions`).

## Orchestration modes

The portable [workflow extension](../references/orchestration.md) owns authority, durable progress, context reduction, and targeted proof. Amp binds it to native `create_thread`, `Task`, collection, status, messaging, and file-transfer tools. Use those tools when available. Native execution records actual receipts through the installed `orchestrate/scripts/tools/native.ts`; it does not invoke the CLI or bridge to delegate. A root exists only when the work needs a separate owner or environment. Keep the dispatcher as the delivery relay unless authority is explicitly transferred.

The CLI/bridge mappings below describe the existing standalone scripted adapter, not permission to bypass native-tool restrictions. Select that mode explicitly before kickoff. Its `run` refuses native-owned workspaces. A shell wait timeout leaves a process running; follow its process handle until it exits instead of launching a duplicate loop. Archiving a thread does not stop its active writer.

### Dispatch constraints

Apply the current tool schemas before the role mappings below. `Task` takes a prompt and description, not model, effort, speed, environment, named subagent type, or readonly fields. Put role-file paths and read-only requirements in the prompt. Use it for bounded parallel assignments or useful context isolation. `create_thread` requires separately owned work, a required different environment, or an explicit request; a model preference alone does not justify another thread. Select only configured and available modes, and report unavailable diversity rather than inventing slugs. `oracle` is for an explicit user request or a specific unresolved high-impact question under its tool contract, not a routine review gate. Source: the active Amp `Task`, `create_thread`, and `oracle` tool schemas.

Prefer supported event subscriptions for exposed events. Time-based monitoring uses `building-schedules` only within an explicit scheduling or monitoring request. A wake does not authorize new external actions. Separate orbs exchange exact files and receipt deltas through supported messaging and file-transfer tools, not shared local paths. Source: active Amp subscription, scheduling, and file-transfer tools.

### Visible run membership

Use the portable [naming contract](../references/orchestration.md#make-run-membership-visible), even when Amp displays agents as siblings. Native `preflight.naming` supplies dispatcher/root/task titles. Pass the title through `create_thread.title` or the prefix through `Task.description`; both fields exist in the native tool schemas. Carry full run identity and dispatcher/state references in the prompt. Use supported thread inspection/rename tools if exposed in the current session; otherwise record that naming could not be inspected or repaired. A blocking Task may expose only its call result, not a durable thread or rename operation. Preserve that distinction in its receipt. Labels are optional and require their own applicable authorization; do not substitute them for the required title/description.

Standalone scripted execution retains its persisted run tag and puts it before custom titles, including shortened titles. Its existing first-poll rename checks handle bridge-created titles; a failed rename stays an attention item. Neither path treats title text or `parent:` search results as proof of ownership.

## Destination

- **Skills directory**: the user's choice among the locations discovery records in `skills.locations`; ask when they have not said. In Amp there are three. The Workspace Skills repository (clone at `~/.cache/amp/repositories/ampcode.com-workspace-skills`) shares the skills with every workspace member. The User Skills repository keeps them personal. A project's `.agents/skills/` limits them to that project. For either repository, prepare its clone by fetching and `git reset --hard origin/main`, or clone it with the command `amp skills repositories` prints for it; that output must list it as writable. Source: `building-skills` skill.
- **Publish**: for a skills repository, commit in the clone, then `git push` after the user confirms; a push to the Workspace Skills repository changes skills for every workspace member. For `.agents/skills/`, the files take effect in that checkout, and committing them follows the project's own process. Source: `building-skills` skill.
- **Reload**: after publishing, as discovery records in `skills.reload`.
- **Name shadowing**: local, built-in, and personal skills mask a workspace skill with the same name. Source: ampcode.com/docs/customize/skills, "Skill Sources and Precedence".
